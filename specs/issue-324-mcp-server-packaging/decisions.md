# MCP Server Packaging — Decisions

## D1: Server composition model

**Choice:** Composable — single server loads tools from multiple domain projects via classpath composition
**Alternatives:**
- Separate only — one server per domain project, no cross-domain. Simpler but requires running multiple servers
- Combined only — one server with everything. Simplest packaging but bloated for single-domain use
**Rationale:** Server is domain-agnostic. A connectors-only, neocortex-only, or combined server are all different dependency sets in the config module's pom.xml. No architectural difference — just what lands on the classpath. Tool name collisions mitigated by domain-prefixed naming convention — catalog generator should reject duplicates at build time.
**Trade-offs:** Config module authors must understand which @McpDomain modules to include.
**Sources:** Platform mcp module architecture (GraphQLModelScanner auto-discovers all @McpDomain beans on classpath)
**Exploration:** quick
**Status:** captured

## D4: Tool catalog source

**Choice:** Per-module manifests generated by extending existing `GraphQLResolverProcessor` APT — each @McpDomain module's APT pass emits a `META-INF/casehub-mcp/<domain>.json` manifest containing tool names and JSON schemas alongside the resolver/REST/plugin code it already generates. At startup, the server scans `ClassLoader.getResources("META-INF/casehub-mcp/")`, reads all fragments, merges into a single tool catalog. Pure classpath resource loading — native-image-safe, sub-millisecond aggregation.
**Alternatives:**
- New standalone catalog generator plugin — duplicates scanning logic already in GraphQLResolverProcessor
- First-call runtime scanning — adds startup latency
- Jandex-only approach — different technology, different integration point than APT
**Rationale:** GraphQLResolverProcessor (in `graphql-generator`) already scans @McpDomain via Jandex indexes and generates source files. Extending it to also emit JSON manifests is incremental work, not a new mechanism. Each domain module independently produces its catalog fragment. Composability comes from classpath — whatever JARs are present, their manifests are aggregated.
**Trade-offs:** Catalog is frozen at module build time. Dynamic tool registration (providers adding tools at runtime) requires notifications/tools/list_changed. Ties manifest format to APT processor.
**Sources:** mcp-standalone-test proves Jandex scanning works without casehub-platform-api; McpDomainJandexScanner in graphql-spring-generator; GraphQLResolverProcessor in graphql-generator
**Exploration:** quick
**Status:** revised (R1-05 — clarified mechanism, aligned with existing APT infrastructure)

## D6: Client-facing MCP transports

**Choice:** stdio + Streamable HTTP — flag to select (--transport=stdio default, --transport=http for remote). Streamable HTTP supersedes SSE in MCP spec 2025-03-26. `quarkus-mcp-server` handles both — no custom protocol implementation needed.
**Alternatives:**
- stdio only — simplest, covers Claude Desktop and langchain4j but no remote access
- SSE only — deprecated by Streamable HTTP, maintained for backward compatibility only
**Rationale:** stdio for local agent frameworks (Claude Desktop, langchain4j). Streamable HTTP for web/container deployments. Both handled by `quarkus-mcp-server` — zero custom protocol code.
**Trade-offs:** None significant — `quarkus-mcp-server` provides both transports out of the box.
**Sources:** MCP spec 2025-03-26 Streamable HTTP transport; quarkus-mcp-server extension
**Exploration:** quick
**Status:** revised (R1-06 — updated from SSE to Streamable HTTP per MCP spec evolution)

## D7: Explicit mode domain filtering

**Choice:** Single config property (`casehub.mcp.domains`) drives filtering at both the tool catalog level and the CDI bean activation level. Quarkus `@IfBuildProperty` / build profiles exclude CDI beans for unconfigured domains at build time — no runtime waste.
**Alternatives:**
- Catalog-only filtering (backend loads all) — wastes resources starting unused providers, loading seed data, establishing connection pools
- Backend-only filtering — works but loses instant-catalog benefit from pre-built manifests
**Rationale:** One config property, applied at build time. Unconfigured domain providers don't load, don't establish connections, don't consume memory. The mechanism already exists in the platform (`@Alternative @Priority` tiers, `@IfBuildProperty`).
**Trade-offs:** Build-time filtering means changing domains requires a rebuild. Runtime-only filtering (without rebuild) can use the full catalog but won't save startup resources.
**Sources:** #323 explicit mode discussion; Quarkus build-time CDI elimination; platform precedent (memory-inmem/memory-jpa @Alternative tiers)
**Exploration:** quick
**Status:** revised (R1-08 — backend now also filters via same config property)

## D8: Platform module structure

**Choice:** Extend existing platform modules rather than creating parallel ones. Two changes: (1) extend `GraphQLResolverProcessor` in `graphql-generator` to emit `META-INF/casehub-mcp/<domain>.json` manifests alongside existing resolver/REST/plugin generation; (2) add an `mcp-server` BOM/archetype that declares the dependency set for a standalone MCP server app (pulls in platform `mcp` + `quarkus-mcp-server` + domain modules). The existing `mcp-core` (CDI-free, native-safe) and `mcp` (Quarkus runtime) modules stay unchanged.
**Alternatives:**
- Three new modules (original D8) — `mcp-catalog-generator`, `mcp-proxy`, `mcp-server`. Creates 8 total MCP modules, duplicates existing capability
- Extend `mcp` module directly — adds server packaging concerns to the runtime module
**Rationale:** The platform already has 5 MCP modules covering annotations, core model, schema building, Quarkus runtime, and Spring runtime. The catalog generation is a natural extension of `GraphQLResolverProcessor` (which already scans @McpDomain and generates code). The server BOM is the only genuinely new artifact. No proxy module needed — `quarkus-mcp-server` handles MCP protocol natively.
**Trade-offs:** `GraphQLResolverProcessor` gains another output format (JSON manifests). The processor is already complex with three outputs (GraphQL, REST, Plugin). A fourth output must not break existing generation.
**Depends on:** D4 (catalog generation mechanism)
**Sources:** Platform mcp module architecture survey; mcp-standalone-test; graphql-generator GraphQLResolverProcessor
**Exploration:** quick
**Status:** revised (R1-03, R1-04 — build on existing modules, no proxy needed)

## D10: Authentication model (new — from R1-12)

**Choice:** Deferred to implementation. stdio transport inherits process identity (no auth needed). HTTP transport authentication is a future concern — for the initial release, HTTP transport is opt-in and should document that it has no built-in auth. The `CurrentPrincipal` provider for standalone use returns an anonymous principal.
**Alternatives:**
- Full auth from day one (API key, OAuth2) — delays initial release for a capability most early adopters don't need
- Delegate to reverse proxy — common pattern (nginx, Envoy handles auth), server stays simple
**Rationale:** Initial target is local agent frameworks (Claude Desktop, langchain4j CLI) over stdio. HTTP transport is secondary. Adding auth complexity before validating the core tool-serving experience is premature. Document the limitation explicitly.
**Trade-offs:** HTTP transport is insecure until auth is added. Must be clearly documented as "local/trusted network only" for HTTP mode.
**Sources:** R1-12 review finding; MCP spec does not mandate authentication
**Exploration:** quick
**Status:** captured
